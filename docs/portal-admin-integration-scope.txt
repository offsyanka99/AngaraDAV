================================================================================
AngaraDAV — Scope of Work: New Administrative Portal inside the User Portal
================================================================================

Document status : Planning / scope definition
Product version : 2.0.0 (portal Administration integration)
Related study   : Admin vs User portal redesign safety investigation (prior session)
Date            : 2026-08-04

--------------------------------------------------------------------------------
1. Purpose and product intent
--------------------------------------------------------------------------------

Implement a new administrative experience integrated into the existing User
Portal (/portal/), visually and interaction-wise consistent with that portal
(dark SPA shell, topnav, tabs/sections, modals, tables).

The new admin UI MUST run in parallel with the classic Web Admin (/admin/)
until feature parity and operational confidence allow deprecation of /admin/
(except possibly install/upgrade, which may remain on a dedicated path longer).

Goals
  - One look-and-feel for day-to-day administration and end-user work
  - Admin features reachable from the portal for users with Admin role
  - No forced cutover; classic /admin/ remains fully functional throughout
  - Clear security boundary: only Admin-role portal users may call admin APIs
  - Incremental delivery with testable milestones

Non-goals (initial program)
  - Unifying DAV auth with the classic "admin" password into a single login
    (unless explicitly decided later; default is role-on-DAV-user model)
  - Replacing /admin/install/ in the first milestones (installer can stay on
    classic stack longer because it runs before a working portal session)
  - Rewriting Flake/Formal themselves (legacy admin continues to use them)
  - Changing DAV protocol endpoints or database schema for cosmetic reasons

--------------------------------------------------------------------------------
2. Current architecture summary (constraints)
--------------------------------------------------------------------------------

User portal (/portal/)
  - TypeScript SPA (Vite) served as static assets from html/portal/
  - JSON API under /api/ (Baikal\Portal\*), session cookie BAIKALPORTAL
  - Auth: DAV users (users.digesta1 + realm)
  - Already has: Calendar, Contacts, Tasks, Notes, Files, user menu,
    Admin-role gate for "Administration" section (isAdmin / role)

Classic Web Admin (/admin/)
  - Server-rendered PHP: Flake router, Twig templates, Formal forms
  - Bootstrap 2 + jQuery + Glyphicons
  - Auth: fixed username "admin" + system.admin_passwordhash (separate session)
  - CSRF: session CSRF_TOKEN on POST
  - Shares Page shell with installer (/admin/install/)
  - Surfaces:
      * Dashboard
      * Users (CRUD, delete confirm)
      * Per-user Calendars and Address Books management
      * System Settings (Standard) — large Formal form from Config\Standard
      * Database Settings
      * Login / Logout
      * Install / upgrade (Initialize, Database, VersionUpgrade, …)

Key implication
  There is no admin JSON API today. Integrating admin into the portal requires
  new backend endpoints (or careful reuse of model layer) behind the portal
  session + Admin role check—not merely new SPA screens.

--------------------------------------------------------------------------------
3. Target architecture (parallel dual-admin)
--------------------------------------------------------------------------------

  ┌─────────────────────┐     ┌──────────────────────────────┐
  │  Classic /admin/    │     │  User Portal /portal/        │
  │  (unchanged until   │     │  + Administration section    │
  │   deprecation)      │     │    (Admin role only)         │
  └─────────┬───────────┘     └──────────────┬───────────────┘
            │                                │
            │ POST + Formal                  │ /api/admin/* (new)
            │ session admin                  │ portal session + isAdmin
            ▼                                ▼
     Baikal\Model\*, Config YAML, PDO / DB (shared domain layer)
            │
            ▼
     Classic install/upgrade may stay on /admin/install/ longer

Parallel operation rules
  - Both UIs write the same config and database; last write wins (document this)
  - Portal admin APIs must enforce isAdmin on every route (not only hide UI)
  - Classic /admin/ auth remains independent (admin password)
  - Portal Admin role remains DAV-user based (portal_admin_users / env /
    username "admin" default as already implemented for the shell)
  - Feature flags optional: system.portal_admin_ui_enabled (default true once
    first screens ship) to hide incomplete areas without removing routes

--------------------------------------------------------------------------------
4. Scope of work — high-level phases (recommended order)
--------------------------------------------------------------------------------

Phase 0  Foundations and governance
Phase 1  Backend platform: admin API shell, authz, audit logging
Phase 2  Portal Administration shell (navigation, layout, feature flags)
Phase 3  Read-only Dashboard parity
Phase 4  Users list (read) + detail (read)
Phase 5  Users write (create / update / delete)
Phase 6  Per-user Calendars and Address Books (admin scope)
Phase 7  System Settings (Standard) — read then write
Phase 8  Database Settings — read then write (highest caution)
Phase 9  Hardening, observability, docs, deprecation plan for /admin/
Phase 10 (Optional later) Installer/upgrade SPA or guided flow

Do not start Phase 5+ write paths before Phases 0–2 and automated tests for
authz (non-admin must get 403).

5. Detailed steps
--------------------------------------------------------------------------------

================================================================================
PHASE 0 — Foundations and governance
================================================================================

Step 0.1 — Confirm product decisions (blocking)
  Detail:
    - Who has Admin role: keep portal_admin_users / env / DAV user "admin"
      default, or introduce explicit DB flag later.
    - Whether classic /admin/ remains available indefinitely as "fallback"
      after portal admin reaches parity.
    - Whether changing admin password from portal is allowed in v1.
    - Whether Database settings are in-scope for v1 (recommend: late phase;
      high blast radius).
  Deliverables: short ADR or section in this doc signed off by maintainer.
  Exit criteria: written decisions recorded.

Step 0.2 — Inventory classic Admin capabilities (checklist)
  Detail:
    Map every controller action and Formal field to a portal feature ID:
      ADM-DASH, ADM-USERS-LIST, ADM-USERS-CRUD, ADM-USER-CALS,
      ADM-USER-ABS, ADM-SETTINGS-SYS, ADM-SETTINGS-DB, ADM-LOGIN-CLASSIC,
      ADM-INSTALL-*.
    Note side effects (user delete → file home quarantine, password digest
    regeneration, YAML writes, session invalidation on admin password change).
  Deliverables: feature matrix (spreadsheet or markdown table) with
    parity status: Not started / Read-only / Full / Deferred.
  Exit criteria: matrix complete; no unknown controller actions.

Step 0.3 — Test strategy for dual UI
  Detail:
    - Keep existing MechanicalSoup tests against /admin/ green forever during
      parallel operation (regression guard for classic path).
    - Add PHP unit tests for new admin service layer (mirroring FileServiceTest).
    - Add API tests (PHP or Python) for /api/admin/* authz: anonymous 401,
      non-admin 403, admin 200.
    - Manual QA checklist per milestone for portal Administration screens.
  Deliverables: test plan section in CI; new test files stubs optional.
  Exit criteria: agreement on "definition of done" per phase.

Step 0.4 — Security threat model (lightweight)
  Detail:
    Document threats: privilege escalation (normal DAV user calling admin API),
    CSRF, session fixation, config overwrite races, SSRF via push URL, path
    traversal on files_storage_path, password hash disclosure.
    Require: Admin role check server-side; CSRF on mutating methods; no
    leaking digesta1 or password hashes in API responses; audit log of admin
    mutations.
  Deliverables: short security checklist for PR reviews.
  Exit criteria: checklist accepted.

PHASE 1 — Backend platform: admin API shell
================================================================================
Phase default Grok effort : high
  Rationale: security foundation (authz, CSRF, API shell); mistakes here
  compromise every later admin endpoint. Prefer high for implementation
  sessions; medium only for pure logging wording (1.4).

Step 1.1 — Admin authorization helper
  Grok effort : high
  Detail:
    Centralize portalUserIsAdmin() (already on Portal\App) into a reusable
    Auth or AdminAuth helper. Add requireAdmin(): string username that throws
    ApiException 403 if not admin.
    Ensure login/me already return isAdmin/role (already partially done).
  Deliverables: Baikal\Portal\AdminAuth or method on Auth; unit tests.
  Exit criteria: non-admin cannot pass requireAdmin().

Step 1.2 — API route namespace /api/admin/*
  Grok effort : high
  Detail:
    In Portal\App::dispatch (or dedicated AdminRouter), register prefix
    /admin/* that always:
      - requireUser()
      - requireAdmin()
      - assert CSRF for POST/PUT/PATCH/DELETE
    Return consistent JSON shapes: { error }, { data }, list wrappers.
  Deliverables: dispatchAdminRoutes() skeleton; 404 for unknown admin paths.
  Exit criteria: GET /api/admin/ping → { ok: true } for admin only.

Step 1.3 — Domain service layer (no HTML)
  Grok effort : high
  Detail:
    Introduce Baikal\Portal\Admin\* services that call existing models
    (User, Config\Standard, Config\Database, Calendar, AddressBook) without
    Formal/Twig. Prefer reusing Baikal\Model methods over copy-paste.
    Example: AdminUserService, AdminSettingsService, AdminDashboardService.
  Deliverables: service classes with clear interfaces; no HTML generation.
  Exit criteria: at least Dashboard stats callable from a unit test.

Step 1.4 — Audit / portal logging for admin actions
  Grok effort : medium
  Detail:
    Log mutations at info level to portal_debug.log (or dedicated
    admin_audit.log): who, action, target, result. Never log passwords.
  Deliverables: logging convention; documented in DEPLOYMENT.md.
  Exit criteria: sample create-user log line appears when PORTAL_LOG_LEVEL=info.

PHASE 5 — Users (write) — CRITICAL PATH
================================================================================
Phase default Grok effort : high
  Rationale: highest operational value and high data-loss / auth risk
  (create, password digest, delete + file quarantine). Prefer high for
  all write APIs and regression tests; xhigh for delete lifecycle if
  model hooks are unclear. UI modals can be medium once APIs are solid.

Step 5.1 — API: POST /api/admin/users (create)
  Grok effort : high
  Detail:
    Body: username, displayname, email, password, password confirm.
    Reuse Baikal\Model\User creation logic (principal, default calendar/AB
    if that is current model behavior—verify against classic).
    Validation parity with Formal rules.
  Exit criteria: creating user via API appears in classic admin and DAV login.

Step 5.2 — API: PATCH /api/admin/users/{username}
  Grok effort : high
  Detail:
    Update displayname, email, password (optional empty = leave unchanged).
    Digest recompute on password change.
  Exit criteria: password change works for portal and DAV.

Step 5.3 — API: DELETE /api/admin/users/{username}
  Grok effort : xhigh
  Detail:
    Mirror classic delete: confirmation required in UI; server may require
    ?confirm=1 or body { confirm: true }.
    Must trigger file home quarantine if files enabled (existing User model
    hooks—verify and test).
  Exit criteria: FileHome lifecycle tests still pass; user gone from DAV.

Step 5.4 — UI: create / edit / delete modals
  Grok effort : medium
  Detail:
    Use standard portal modals (header/body/footer). Delete confirm lists
    consequences. Never show existing password.
  Exit criteria: full CRUD via portal only; classic admin still works.

Step 5.5 — Regression tests
  Grok effort : high
  Detail:
    PHP unit tests for AdminUserService; optional Python API tests.
    Keep classic MechanicalSoup users tests green.
  Exit criteria: CI green.

PHASE 7 — System Settings (Standard)
================================================================================
Phase default Grok effort : high
  Rationale: many Formal fields, YAML write integrity, admin password and
  service flags with real runtime impact. GET can be medium; write path
  and validation tests should be high (xhigh if touching password_hash
  or atomic config write unfamiliar code).

Step 7.1 — API: GET /api/admin/settings/system
  Grok effort : medium
  Detail:
    Return editable settings as JSON (booleans, strings, numbers). Map from
    Baikal\Model\Config\Standard / baikal.yaml system section.
    Do not return admin_passwordhash; return hasAdminPassword: true/false.
  Exit criteria: values match YAML after admin UI load.

Step 7.2 — API: PUT/PATCH /api/admin/settings/system
  Grok effort : xhigh
  Detail:
    Validate each field with same constraints as Formal morphology
    (ranges for MB upload/quota, push URL rules, etc.).
    Atomic YAML write; preserve unknown keys if any.
    Admin password change: only if both password fields non-empty and match;
    use password_hash() path already used by classic.
    Document: changing session_max_age affects both portals' idle behavior
    as configured.
  Exit criteria: toggle files_enabled via portal admin; classic shows same.

Step 7.3 — UI: System settings form
  Grok effort : medium
  Detail:
    Group fields like classic (DAV services, files, push, session, admin
    password). Use portal form controls; section help (i) optional.
    Link "Open classic settings" during parallel phase.
  Exit criteria: can perform a full save cycle without YAML corruption.

Step 7.4 — Tests
  Grok effort : high
  Detail:
    Unit tests for settings validation; file write to temp YAML.
    Manual checklist for push/files dangerous fields.
  Exit criteria: CI + manual sign-off.

PHASE 8 — Database Settings (highest caution)
================================================================================
Phase default Grok effort : high
  Rationale: credentials surface + brick-instance risk. Read-only display is
  medium if password never leaves the server; any write implementation is
  xhigh and should stay gated/deferred unless product elevates it.

Step 8.1 — Read-only first: GET /api/admin/settings/database
  Grok effort : medium
  Detail:
    Show backend type, host, dbname, username; never return password.
    Show sqlite path if applicable.
  Exit criteria: accurate display.

Step 8.2 — Write path (optional gate)
  Grok effort : xhigh
  Detail:
    Only after explicit product approval. Changing DB settings can brick the
    instance. Prefer: require typing CONFIRM
  Recommendation: DEFER write to post-parity or keep classic-only for DB.
  Exit criteria: documented decision; if deferred, UI shows classic link only.

  Product decision (2026-08-05, implemented):
    Portal database WRITE is DEFERRED / classic-only.
    GET /api/admin/settings/database is read-only; mutating methods return 403
    with pointer to /admin/?/settings/database. UI shows connection summary
    without secrets and a primary classic fallback link.

--------------------------------------------------------------------------------
7. Ordering rationale (why this sequence)
--------------------------------------------------------------------------------

  1. Authz platform first — prevents shipping UI that cannot be secured.
  2. Shell second — establishes navigation without irreversible data writes.
  3. Read-only dashboard/users — low risk, validates API + UI integration.
  4. User writes next — highest operational value, well-understood domain.
  5. Nested resources — depends on user APIs.
  6. System settings — YAML writes; needs mature validation/tests.
  7. Database settings last — highest downtime risk.
  8. Installer last/never — different lifecycle from day-to-day admin.

--------------------------------------------------------------------------------
9. Risks and mitigations
--------------------------------------------------------------------------------

  Risk: Privilege escalation via missing requireAdmin
    Mitigation: central requireAdmin(); CI tests for 403; code review checklist.

  Risk: YAML corruption on settings save
    Mitigation: validate fully; write temp + rename; backup note in docs;
    unit tests on temp filesystem.

  Risk: Dual UI config races
    Mitigation: document last-write-wins; short-term acceptable for single-admin
    homes; optional ETag/version field later.

  Risk: Incomplete parity confuses operators
    Mitigation: feature matrix in UI; classic links; portal_admin_ui capabilities.

  Risk: User delete misses file quarantine / principal cleanup
    Mitigation: call existing model delete path; extend FileHome tests.

  Risk: CI DOM tests break if classic admin is casually edited
    Mitigation: freeze classic HTML contracts during parallel phase; only
      fix bugs in classic unless necessary.

  Risk: Scope creep into installer rewrite
    Mitigation: Phase 10 explicitly deferred.

--------------------------------------------------------------------------------
10. Definition of "fully implemented" (exit from parallel mode)
--------------------------------------------------------------------------------

  All of the following:
    [ ] Feature matrix 100% for day-to-day admin (Dashboard, Users CRUD,
        per-user Cal/AB, System settings; DB write either portal or explicitly
        classic-only by product decision)
    [ ] Automated tests for admin API authz and critical writes
    [ ] Classic /admin/ still works (or intentionally disabled with flag)
    [ ] Documentation updated for operators (TrueNAS compose notes if needed)
    [ ] At least one production-like dual-run period with no P0 regressions
    [ ] Deprecation announcement prepared for classic UI (if desired)
